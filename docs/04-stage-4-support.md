# Этап 4. Поддержка и развитие

**Начало:** 08.02.2027, с выходом R1 · **Длительность:** постоянно · **Ресурсы:** 20–30% команды во время активной разработки (R1.1–R2.1), после R2.1 — 1–1,5 ставки плюс разработка по дорожной карте

← [Второстепенные функции](03-stage-3-secondary-features.md) · [К плану](README.md)

## Цель

Пилот должен работать стабильно и предсказуемо в учебное время, качество ответов не должно падать, а данные пользователей — оставаться защищёнными. Пиковые сезоны (начало семестра, сессии) нужно проходить без сбоев, а продукт — развивать по обратной связи.

## 1. Организация поддержки

| Роль | Кто | Обязанности |
|---|---|---|
| Дежурный инженер | Ротация раз в неделю: Р1 → Р4 → Р3 | Реакция на алерты и обращения, первичная диагностика, решение о хотфиксе или откате |
| Ответственный за модели | Р3 | Качество ответов, ночные оценки, обновление моделей |
| Ответственный за клиентские релизы | Р2 | Сборки, магазины, автообновление, совместимость |
| Ответственный за инфраструктуру | Р4 | Сервер, резервные копии, безопасность, стоимость |
| Владелец продукта | Р1 или заказчик | Приоритеты, связь с вузом, отчёты |

**Часы поддержки в пилоте:** учебные дни с 8:00 до 22:00 МСК. В остальное время — по возможности. Во время сессий дежурный доступен с 8:00 до 23:00.

## 2. Классификация инцидентов и SLA

| Приоритет | Примеры | Реакция | Восстановление или обходной путь |
|---|---|---|---|
| **P1 — критичный** | Сервис недоступен; массово не работает вход; подозрение на утечку данных | 30 мин | ≤ 4 ч; разбор инцидента (постмортем) в течение 3 рабочих дней |
| **P2 — высокий** | Не работает ключевая функция: голос, документы, расписание | 2 ч | ≤ 1 рабочего дня |
| **P3 — средний** | Ошибка с обходным путём, заметное падение качества ответов | 1 рабочий день | В ближайшем патче, ≤ 2 недель |
| **P4 — низкий** | Косметика, пожелания | 3 рабочих дня | В бэклог |

Если инцидент может касаться персональных данных (например, в загруженных пользователями документах), сразу подключаем юриста. Если данные признают ПД, по 152-ФЗ о неправомерной передаче нужно уведомить Роскомнадзор в течение 24 часов, а о результатах расследования — в течение 72 часов. Регламент такого уведомления готовим заранее.

## 3. Мониторинг и SLO

| Показатель | Цель (SLO) | Алерт |
|---|---|---|
| Доступность API в 8:00–22:00 МСК | ≥ 99% в месяц (пилот), ≥ 99,5% с R2.1 | Внешняя проверка не проходит 2 мин подряд |
| Первый токен ответа | p95 ≤ 1,5 с | p95 > 2 с в течение 10 мин |
| Голос: от конца речи до звука | p95 ≤ 2,5 с (R1), ≤ 1,5 с (R2) | p95 выше цели +1 с в течение 10 мин |
| Доля ошибок API (5xx) | < 1% | > 2% за 5 мин |
| Очередь документов | p95 ожидания ≤ 2 мин | > 10 мин |
| Конспект часовой лекции | ≤ 15 мин | > 30 мин |
| Определение места (R2) | p95 ≤ 5 с, Top-1 ≥ 85% (по выборочной проверке) | p95 > 8 с |
| GPU | Загрузка в пик ≤ 70%, память без OOM | > 85% 30 мин; любой OOM |
| Диск | Свободно ≥ 20% | < 15% |
| Резервные копии | Ежедневная копия успешна | Пропуск копии |
| Адаптер расписания | Синхронизация успешна | Ошибка или резкое изменение объёма данных |

**Инструменты:** Prometheus и Grafana, Loki (логи без ПД), GlitchTip (ошибки клиента и сервера), Uptime Kuma (внешние проверки и страница статуса).

**Алерты** уходят в чат команды. В них нет содержимого запросов и идентификаторов пользователей.

## 4. Релизы

**Клиент:**

- Патчи — по необходимости, обычно раз в 1–2 недели. Минорные версии — раз в 4–6 недель. Функциональные релизы — по дорожной карте.
- Раскатка поэтапная: сначала бета-канал (бета-группа, около 10% пользователей), через 2–3 дня — все.
- При несовместимом изменении API клиент обновляется принудительно; старые версии API поддерживаются не меньше 4 недель.
- Каналы: RuStore, APK с сайта (проверка обновлений в приложении), встроенное автообновление для Windows и Linux.

**Сервер:**

- Деплой — в рабочие дни до 16:00. Не деплоим в дни экзаменов и перед массовыми дедлайнами.
- Обновление без простоя (два экземпляра API), откат ≤ 10 мин.
- Миграции БД — только обратно совместимые (схема «расширить, потом сузить»).
- Новые функции включаются флагами, сначала для бета-группы.

## 5. Жизненный цикл моделей

1. **Ежеквартальный обзор** новых открытых моделей:
   - сначала проверка лицензии: разрешено ли коммерческое использование;
   - затем бенчмарк на наших наборах;
   - канареечный запуск на 10% запросов на 1 неделю;
   - полное переключение.
2. **Фиксация версий.** У каждой модели хэш весов и «паспорт»: версия, лицензия, дата, результаты оценки, конфигурация квантования. В метаданных каждого ответа хранится версия модели. Так оператор системы ИИ может объяснить, какая модель дала ответ; это учитывает требования 243-ФЗ.
3. **Регрессия.** Перед любым обновлением модели или промптов прогоняются ночные наборы. Падение метрики больше чем на 3 п. п. блокирует обновление. Откат — заменой конфигурации, ≤ 15 мин.
4. **Готовность к замене на российскую модель.** GigaChat всегда держим в бенчмарке. Если подзаконные акты по 243-ФЗ потребуют суверенные или национальные модели в образовании, переключение займёт дни, а не месяцы.
5. **Ежемесячный разбор оценок 👎.** Выборочно и обезличенно, только по ответам, которые пользователь отправил вместе с оценкой. Причины классифицируются: модель, поиск по документам, распознавание речи, интерфейс.

## 6. Данные: хранение и резервные копии

| Данные | Срок хранения |
|---|---|
| Сообщения чатов | По умолчанию 90 дней, пользователь выбирает 7, 30 или 90 дней либо «не хранить»; «инкогнито» — не хранится |
| Документы и их индекс | До удаления пользователем или 12 месяцев неактивности аккаунта (с предупреждением в приложении) |
| Аудио голосовых запросов, кадры камеры | Не хранятся |
| Аудио лекций | Удаляется после распознавания (по умолчанию) |
| Технические логи | 14 дней |
| Метрики | Агрегаты — 13 месяцев |
| Резервные копии | Ежедневно, шифрование, хранилище в другом ЦОД в РФ, хранение 30 дней |

**Восстановление.**

- Раз в квартал проверяется восстановление из копии на чистый сервер с замером времени. Цель — ≤ 4 ч (RTO); потеря данных — не больше суток (RPO).
- После удаления аккаунта данные исчезают из копий при их ротации, в течение 30 дней.

## 7. Безопасность

- Обновления ОС и зависимостей — ежемесячно (Renovate или Dependabot). Критические уязвимости закрываются в течение 72 часов.
- Сканирование образов и зависимостей (Trivy) — в каждом CI.
- Ротация секретов и ключей — раз в 6 месяцев и при уходе участника команды. Ревизия доступов — раз в квартал.
- Админ-панель доступна только через VPN и с 2FA. Все действия администраторов журналируются.
- Перед масштабированием на весь вуз — внешний пентест.
- Мониторинг злоупотреблений: аномальная частота запросов, перебор паролей, массовая регистрация по одному коду.

## 8. Сезонные операции

| Период | Что происходит | Действия |
|---|---|---|
| Конец августа | Новый учебный год, первокурсники | Импорт групп и расписания, новые коды приглашения, проверка навигации после летних ремонтов, режим первокурсника, увеличение GPU при необходимости |
| Сентябрь | Пик регистраций и навигации | Усиленное дежурство, ежедневный обзор нагрузки |
| Декабрь – январь | Зачёты и экзамены | Пик запросов по документам и конспектам; временный дополнительный GPU (почасовая аренда); заморозка рискованных релизов |
| Февраль | Весенний семестр | Импорт нового расписания, коды для новых групп |
| Май – июнь | Летняя сессия | Как в декабре – январе |
| Июль | Каникулы | Плановые работы: обновления моделей и ОС, миграции, проверка восстановления, оцифровка корпусов |

## 9. Поддержка пользователей

**Каналы:**

- в приложении — «Сообщить о проблеме»: анонимно, технический журнал прикладывается только с согласия пользователя;
- FAQ на сайте;
- новостной канал в мессенджере.

Ответ — в течение 1 рабочего дня.

**Обратная связь.** Раз в неделю разбираем обращения и оценки 👎 и переносим выводы в бэклог. Раз в месяц проводим короткий анонимный опрос пилотной аудитории.

**Работа с вузом.** Есть контактное лицо в вузе (по расписанию, кампусу, кодам) и ежемесячная встреча по итогам пилота.

## 10. Сопровождение источников данных

- **Расписание.** Синхронизация проверяется ежедневно, алерт срабатывает при изменении структуры сайта или резком изменении объёма данных. Есть регламент ручного импорта по шаблону Excel. Источник изменений в вузе (диспетчерская, деканат) должен быть известен.
- **Кампус (с R2).** Пользователь может отметить «здесь всё изменилось» — это создаёт задачу. Изменённые узлы переснимаются; эталонные фото обновляются раз в год, летом.
- **База знаний вуза.** Документы обновляются раз в семестр; у каждого есть дата актуальности.

## 11. Правовое сопровождение

- Пользовательское соглашение и описание обработки данных пересматриваются раз в год и при изменении функций.
- Отслеживаем изменения в 152-ФЗ, правилах авторизации (149-ФЗ в ред. 406-ФЗ), подзаконных актах 243-ФЗ, требованиях RuStore.
- Лицензии моделей и библиотек учитываются в файле `THIRD_PARTY_NOTICES`. CI проверяет, что все лицензии из разрешённого списка.

## 12. Метрики продукта и отчётность

- **Еженедельный дашборд** (только агрегаты):
  - активные пользователи;
  - запросы: текст и голос;
  - работа с документами и конспектами;
  - определения места (с R2);
  - доля 👍/👎;
  - ошибки;
  - стоимость инфраструктуры в расчёте на активного пользователя.
- **Ежемесячный отчёт** заказчику и вузу: метрики, инциденты, планы.
- **Ежеквартальное планирование:** пересмотр дорожной карты и бэклога R3.

## 13. Управление стоимостью

- Ежемесячный учёт расходов на инфраструктуру и расчёт стоимости на активного пользователя.
- Масштабирование по сезону: дополнительный GPU берётся почасово на сессию и начало семестра.
- Способы экономии:
  - квантование моделей;
  - кэш ответов на частые вопросы о вузе;
  - простые запросы (расписание, справка) уходят на компактную модель;
  - пакетная обработка конспектов в часы низкой нагрузки.
- Скидки за длительную аренду рассматриваем после стабилизации нагрузки.

## 14. Регламенты (runbooks)

Готовим к R1 и поддерживаем в `docs/runbooks/`:

1. Перезапуск сервисов и проверка работоспособности.
2. Откат релиза сервера и клиента.
3. Переключение и откат модели.
4. Восстановление из резервной копии на новый сервер.
5. Ротация ключей шифрования и секретов.
6. Подключение дополнительного GPU на пик нагрузки.
7. Блокировка злоупотреблений: отзыв кода приглашения, блокировка аккаунта.
8. Ручной импорт и исправление расписания.
9. Обновление графа и эталонных фото навигации (с R2).
10. Действия при подозрении на утечку данных.

## 15. Документация и передача знаний

- У каждого сервиса есть README: как запустить, конфигурация, зависимости.
- Решения фиксируются в ADR, API — в актуальном OpenAPI.
- Новый участник должен начать работать за ≤ 2 дней: скрипт локального окружения, тестовые данные, гайд.
- Задачи ротируются между участниками, чтобы снизить «фактор автобуса».
