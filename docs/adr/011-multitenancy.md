# ADR-011. Несколько вузов в одной установке с первого дня

Статус: принято, 16.11.2026. Расширяет план: в исходном плане несколько вузов появлялись только в R3.

## Решение

Иерархия: вуз (tenant) -> кампусы -> корпуса -> этажи. Почти каждая таблица содержит `tenant_id`. Пользователь принадлежит одному вузу, вуз определяется кодом приглашения.

Изоляция в PostgreSQL через Row-Level Security. API для каждого запроса выставляет `app.tenant_id` и `app.user_id` в транзакции, политики не дают прочитать чужие строки, даже если в коде забыли условие.

У вуза свои: учебный календарь и часовой пояс, источники расписания, база знаний, коды приглашения, настройки (например, хранить ли ФИО преподавателей), привязки моделей (адаптер LoRA, профиль ASR, индекс фото кампуса, голос и модель слова активации).

## Варианты развёртывания

- Общий сервер на несколько вузов: один стек, модели и GPU делятся.
- Установка у вуза: тот же код и те же плейбуки, в БД один вуз.

## Последствия

- Чуть сложнее запросы и тесты, зато переход к нескольким вузам не требует миграции данных.
- Суперадмин видит все вузы, администратор вуза только свой.
